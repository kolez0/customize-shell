# Спецификация: переносимая конфигурация zsh с Antidote и Starship

## Цель

Создать переносимый проект пользовательской конфигурации zsh, который упрощает ежедневную работу в терминале на macOS и Linux. Конфигурация должна давать удобную историю команд, автодополнение, поиск команд и файлов, полезные алиасы, плагины zsh и единый prompt Starship. Установка и удаление должны быть понятными и безопасными для уже существующих пользовательских настроек.

## Правила документации проекта

- Вся документация проекта хранится в каталоге `docs/`, кроме `README.md`, который размещается в корне репозитория как главная страница проекта.
- Документация ведётся на русском языке; названия команд, файлов, переменных, API и общепринятые технические термины сохраняются в оригинальном написании, когда перевод ухудшает точность.
- Новые документы размещаются непосредственно в `docs/` либо в тематических подкаталогах внутри `docs/`; корневой `README.md` является единственным исключением.

## Целевая аудитория и сценарий

Проект предназначен для одного пользователя, который хочет поддерживать одинаковую базовую среду zsh на нескольких компьютерах. Основной сценарий: клонировать репозиторий, запустить установщик, получить конфигурацию и при необходимости безопасно вернуть прежние настройки.

## Целевые платформы

- macOS с установленным Homebrew.
- Debian и Ubuntu с `apt`.
- Fedora с `dnf`.
- Arch Linux с `pacman`.
- Поддерживаются только версии macOS и выпуски Debian, Ubuntu и Fedora, для которых поставщик ОС предоставляет обновления безопасности на момент выпуска проекта; для Arch Linux поддерживается актуальная rolling-release-система. Матрица проверенных версий указывается в документации каждого выпуска.
- zsh должен быть предварительно установлен; установщик проверяет его наличие, но не устанавливает и не меняет оболочку пользователя.
- Установщик автоматически устанавливает недостающие необходимые утилиты: сначала использует подходящий пакет из системного репозитория, а если он отсутствует или не соответствует требованиям — официальный способ установки от разработчиков утилиты.

Установщик должен учитывать различия платформ, не предполагать фиксированный путь Homebrew и использовать соответствие имён пакетов для поддерживаемых систем. Остальные ОС и дистрибутивы Linux не входят в первую версию: при их обнаружении установщик сообщает об ограничении до изменения конфигурации.

## Согласованные архитектурные решения

- Установщик реализуется на POSIX `sh`, чтобы работать на целевых macOS и Linux без дополнительного runtime.
- Конфигурация хранится в репозитории dotfiles.
- Antidote устанавливается клонированием официального репозитория `https://github.com/mattmc3/antidote.git` в `${ZDOTDIR:-$HOME}/.antidote` и подключается из `antidote.zsh` в этом каталоге.
- Antidote управляет сторонними плагинами по декларативному списку `.zsh_plugins.txt` и генерирует статический файл загрузки плагинов. Плагины не закрепляются на commit SHA: они следуют актуальным версиям upstream и обновляются только явным вызовом функции `zplugin-update`.
- Starship отвечает за prompt; встроенные темы и prompt Oh My Zsh не используются.
- Установщик копирует управляемые файлы из репозитория в пользовательские каталоги; симлинки не используются. Файлы проекта размещаются в `${XDG_CONFIG_HOME:-$HOME/.config}/customize-zsh/`, а `starship.toml` — в `${XDG_CONFIG_HOME:-$HOME/.config}/starship.toml`. Переменная `STARSHIP_CONFIG` указывает Starship на этот файл.
- Репозиторий является источником конфигурации. Повторный запуск установщика переносит новые версии файлов в домашний каталог.
- Существующий `~/.zshrc` не заменяется: установщик добавляет в конец один помеченный блок подключения конфигурации проекта и не трогает остальное содержимое, включая настройки, добавленные Яндекс CLI. Повторный запуск обновляет только этот блок.
- Перед полной заменой отличающегося существующего управляемого файла установщик автоматически создаёт резервную копию в `${XDG_CONFIG_HOME:-$HOME/.config}/customize-zsh/backups/`, сохраняя исходное имя и добавляя временную метку; сообщает путь к копии и продолжает без дополнительного запроса подтверждения. `~/.zshrc` целиком не заменяется и в резервную копию не копируется: установщик добавляет или обновляет только свой помеченный блок.
- Настройки разделяются на общие и локальные, чтобы машинные пути и пользовательские интеграции не попадали в переносимую базовую конфигурацию.

## Функциональные требования

### Установка и обслуживание

1. Установщик определяет ОС, её версию и доступный пакетный менеджер до установки зависимостей; продолжает только для релизов из документированной матрицы поддержки.
2. Установщик проверяет наличие zsh и, если он отсутствует, прекращает работу до изменения конфигурационных файлов с инструкцией по его установке. Установщик автоматически устанавливает отсутствующие утилиты из набора Git, Starship, fzf, fd, bat, eza, ripgrep и zoxide; Antidote клонируется из официального GitHub-репозитория в `${ZDOTDIR:-$HOME}/.antidote`.
3. Для системных пакетов в первую очередь используются нативные пакетные менеджеры целевых ОС. Если нужного пакета нет в системном репозитории или доступная версия не подходит, установщик применяет официальный способ от upstream-проекта, например его подписанный пакетный репозиторий или официальный установщик. Сторонние зеркала и неподтверждённые источники не используются. Источник, способ установки и соответствие имён пакетов и исполняемых файлов документируются для каждой целевой платформы.
4. Установщик устанавливает только перечисленные проектом пакеты и не выполняет полное обновление системы или посторонних пакетов.
5. Если подходящий пакетный менеджер отсутствует, система не поддерживается или для недостающей зависимости нет официального способа установки, установщик останавливается до изменения конфигурационных файлов и сообщает, какие зависимости пользователь должен установить вручную.
6. Установщик не запрашивает и не скрывает повышение привилегий самостоятельно. Если пакетный менеджер требует административные права, он выполняет собственный стандартный запрос пароля/подтверждения.
7. Перед полной заменой отличающегося существующего управляемого файла установщик сохраняет резервную копию в `${XDG_CONFIG_HOME:-$HOME/.config}/customize-zsh/backups/`, добавляя временную метку к исходному имени, сообщает её путь и продолжает без запроса подтверждения. Для `~/.zshrc` резервная копия не создаётся: изменяется только помеченный блок, а всё остальное содержимое сохраняется.
8. Установщик размещает конфигурацию проекта в `${XDG_CONFIG_HOME:-$HOME/.config}/customize-zsh/`, `starship.toml` — в `${XDG_CONFIG_HOME:-$HOME/.config}/starship.toml` и устанавливает `STARSHIP_CONFIG` на этот файл. В конец `~/.zshrc` добавляется уникальный помеченный блок подключения. Если `.zshrc` отсутствует, он создаётся с этим блоком. Иные строки `.zshrc` не редактируются и не удаляются.
9. Установщик клонирует плагины и генерирует статический файл загрузки при установке. При запуске zsh подключает готовый статический файл; сеть не используется.
10. В конфигурации zsh доступна функция `zplugin-update`, аналогичная функции из исходного `.zshrc`. Она обновляет Antidote и плагины командой `antidote update`, затем пересоздаёт статический файл по `.zsh_plugins.txt`. Новый файл сначала формируется во временный файл и заменяет рабочий только после успешного обновления и генерации. При ошибке функция сообщает причину, возвращает ненулевой код и сохраняет прежний статический файл. Функция не обновляет Git-репозиторий проекта и не копирует конфигурацию; для синхронизации файлов из локальной копии репозитория пользователь повторно запускает `install.sh`. Сетевые запросы для плагинов происходят только при установке или явном вызове `zplugin-update`.
11. Повторный запуск не переустанавливает уже доступные утилиты без необходимости, не копирует неизменившиеся файлы повторно, обновляет существующий блок подключения без дубликатов, не создаёт дубликатов резервных копий при отсутствии изменений и приводит систему к тому же ожидаемому состоянию.
12. Ошибка установки должна завершаться ненулевым кодом и объяснять причину. Если ошибка возникла после начала установки конфигурации, установщик автоматически восстанавливает из резервных копий целые файлы, заменённые в текущем запуске, и удаляет новые целевые файлы, созданные этим запуском. В `~/.zshrc` он возвращает помеченный блок к состоянию до текущего запуска, не затрагивая остальные строки; результат отката сообщается пользователю.
13. Удаление конфигурации снимает только помеченный блок проекта из `~/.zshrc`, сохраняя все остальные строки, включая добавленные другими установщиками; затем восстанавливает управляемые файлы из их резервных копий или удаляет файлы, созданные проектом. Резервные копии сохраняются.
14. Документация описывает установку, поддерживаемые пакетные менеджеры, зависимости, расположение резервных копий, обновление проекта и плагинов, а также безопасное удаление и восстановление конфигурации.

### Конфигурация zsh

- История команд хранится в `${XDG_STATE_HOME:-$HOME/.local/state}/zsh/history`; каталог создаётся при необходимости. Задаются разумный большой лимит, совместная история сессий и фильтрация дубликатов/команд с начальным пробелом.
- Пути к конфигурации проекта и резервным копиям строятся с учётом `$XDG_CONFIG_HOME`; если переменная не задана, используется `$HOME/.config`.
- Если `~/.local/bin` существует, конфигурация добавляет его в начало `PATH`, только если каталог ещё не включён в путь; повторный запуск оболочки не создаёт дубликатов.
- Включаются полезные базовые параметры zsh, включая переход в каталог вводом его имени и интерактивные комментарии.
- Система completions и связанные `zstyle` настраиваются один раз. Файл кэша `zcompdump` хранится в `${XDG_CACHE_HOME:-$HOME/.cache}/zsh/`; каталог создаётся при необходимости.
- Настройки разбиваются на небольшие файлы по назначению (например, базовые параметры, плагины, инструменты, локальные настройки), подключаемые из основной конфигурации.
- Платформенно-зависимые пути и необязательные интеграции подключаются только при наличии соответствующего файла/инструмента.

### Плагины и prompt

- Antidote установлен или подключён установщиком так, чтобы конфигурация могла быть воспроизведена на новом компьютере.
- Состав плагинов хранится в отдельном текстовом списке. Базовый набор первой версии: `zsh-users/zsh-autosuggestions`, `zsh-users/zsh-history-substring-search`, `zdharma-continuum/fast-syntax-highlighting` и `zsh-users/zsh-completions`.
- Порядок загрузки учитывает требования плагинов, в частности `fast-syntax-highlighting` загружается после остальных плагинов.
- Список плагинов не должен включать альтернативный prompt.
- Starship инициализируется только для интерактивной оболочки и настраивается собственным конфигурационным файлом проекта.
- Prompt имеет двухстрочную компоновку. В первой строке текущий каталог выравнивается по левому краю, а модули Git, языков и Kubernetes — по правому краю. Для разделения сторон используется модуль заполнения строки Starship. Во второй строке символ ввода выравнивается по левому краю, а код ошибки и длительность предыдущей команды, если они есть, — по правому.
- Для версий используются только модули Starship `nodejs`, `python`, `golang` и `php`, и только при распознанных Starship файлах или признаках соответствующего проекта.
- Используются модули `git_branch` и `git_status`: они показывают текущую ветку, локальные изменения, а также состояние ahead/behind относительно настроенной удалённой отслеживаемой ветки. Для состояния синхронизации показывается число коммитов. Модули видны только внутри Git-репозитория, используют локальные данные и не выполняют сетевые запросы.
- Модуль `kubernetes` показывается только рядом с маркерами Kubernetes-проекта (например, каталогами `k8s/`, `kubernetes/` или файлами `kustomization.yaml`, `Chart.yaml`). Он показывает текущий контекст и namespace из активной конфигурации (`$KUBECONFIG` либо `~/.kube/config`); пользователь и имя кластера отдельно не выводятся. Контексты, в имени которых отдельным компонентом (без учёта регистра) указано `prod` или `production`, выделяются янтарным цветом без жирного начертания; например, `prod-eu` подсвечивается, а `nonprod-eu` — нет. Остальные контексты отображаются нейтральным цветом.
- Домашний каталог обозначается как `~`; длинные пути сокращаются в середине, при этом начало пути и текущий каталог остаются узнаваемыми.
- При ширине терминала менее 120 колонок используется компактный вариант prompt без версий Node.js, Python, Go и PHP; полный вариант включается при 120 колонках и более. В обоих вариантах путь сокращается в середине с сохранением `~` и текущего каталога, а Git-состояние и Kubernetes-контекст сохраняются. Если модули не помещаются, Starship переносит их на дополнительные строки над строкой ввода. Символ `$` остаётся на последней строке приглашения.
- Длительность команды показывается, если она выполнялась дольше 2 секунд; код ошибки — только после неудачной команды. Порог длительности соответствует значению Starship по умолчанию.
- Цветовая подача сдержанная: цветом выделяются ошибки и изменённое состояние Git; остальные элементы остаются нейтральными и читаемыми.
- Символ ввода — `$`.
- В начале второй строки показывается иконка текущей операционной системы через модуль Starship `os`. Карта Nerd Font: macOS — ``, Debian — ``, Ubuntu — ``, Fedora — ``, Arch Linux — ``. В SSH-сессии после иконки, но перед `$`, показываются имя пользователя и короткое имя удалённого хоста в формате `пользователь@хост`; локально SSH-префикс скрыт. Для определения ОС и SSH-сессии используются штатные модули Starship `os`, `username` и `hostname`.
- Для каталога, ветки Git и обнаруженных сред разработки используются иконки Nerd Fonts из JetBrainsMono Nerd Font Mono. Обычный JetBrains Mono не содержит этот набор добавленных иконок; документация должна указать требование к пропатченному шрифту и объяснить текстовый fallback, если иконки недоступны. Установщик проекта не меняет настройки шрифта терминала.
- Модули версий Starship включаются только при наличии соответствующих файлов/признаков проекта, чтобы не выводить нерелевантные версии в обычных каталогах.

Пример обычного приглашения:

```text
󰉋 ~/projects/.../api                  main* ⇡2 ⇣1 ·  v22 ·  v3.13 ·  v1.23 ·  v8.4 · ☸ prod/default
 $
```

После неудачной или достаточно долгой команды вторая строка показывает код завершения и/или длительность справа от символа ввода:

```text
󰉋 ~/projects/.../api                  main* ⇡2 ⇣1 ·  v22 ·  v3.13 ·  v1.23 ·  v8.4 · ☸ prod/default
 $                                             ошибка 127 · 1,2 с
```

При узком окне терминала версии языков скрываются раньше Git- и Kubernetes-состояния; строка ввода остаётся последней. На второй строке `$` сохраняет левое выравнивание, а статус команды — правое, если он отображается.

В SSH-сессии перед символом ввода дополнительно отображаются пользователь и короткое имя удалённого хоста:

```text
󰉋 ~/projects/api                            main · ☸ prod/default
 nick@build-host $
```

### Удобства командной строки

- Установщик устанавливает `fzf`, `fd`, `bat`, `eza`, `ripgrep` и `zoxide`; интеграции активируются только при наличии соответствующих команд, чтобы конфигурация оставалась устойчивой к частичному удалению утилиты.
- Конфигурация учитывает платформенные варианты имён исполняемых файлов: `fdfind` используется как `fd`, а `batcat` — как `bat`, если команды с обычными именами отсутствуют. Нормализация действует в оболочке пользователя и не создаёт глобальных симлинков.
- Сохраняются сочетания fzf для файлов и истории. Дополнительно `Ctrl+F` открывает поиск файлов через fzf, исключая скрытые файлы; предпросмотр через `bat` включается, если утилита доступна. Поиск файловых сочетаний регистрируется только при наличии `fd` или `fdfind`, поэтому удаление утилит не оставляет неработающие привязки клавиш.
- zoxide обеспечивает быстрый переход по каталогам.
- Переносятся алиасы из текущей конфигурации: `ls`, `ll`, `la` и `tree` для eza; `cat` для bat; `grep` для ripgrep; цветной `diff` при поддержке параметра `--color=auto` и `df -h`. Алиасы создаются только при наличии соответствующих программ либо имеют безопасный fallback.
- Конфигурация не должна жёстко указывать каталоги `/opt/homebrew`, `/Users/<имя>` или другие персональные абсолютные пути.

## Нефункциональные требования

- Обычный запуск интерактивной оболочки не должен выполнять сетевые запросы или обновлять плагины автоматически.
- Обновление Antidote и плагинов выполняется только явным вызовом функции `zplugin-update`; запуск zsh не обновляет их.
- Конфигурация должна оставаться читаемой и изменяемой вручную без генератора.
- Загрузка должна быть достаточно быстрой для интерактивной работы; тяжёлые необязательные интеграции не должны без причины задерживать появление приглашения.
- Установщик должен быть идемпотентным и не изменять файлы вне пользовательской конфигурации и каталога проекта без явной необходимости.

## Границы первой версии

### Включено

- Базовая конфигурация zsh и истории.
- Antidote и компактный список плагинов.
- Starship и базовая конфигурация prompt.
- Автоматическая установка и интеграция fzf, fd, bat, eza, ripgrep и zoxide.
- Установка, резервирование существующих файлов, обновление и инструкция по удалению/восстановлению.

### Не включено

- Автоматическая установка zsh или смена системной оболочки по умолчанию.
- Установка или настройка самого пакетного менеджера, если в системе его нет.
- Перенос всех машинно-зависимых интеграций из текущего `.zshrc` в общую конфигурацию. В частности, специфичные пути Yandex Cloud, Docker Desktop и pipx остаются локальными настройками пользователя.
- Настройка терминального приложения, шрифтов, цветов или окружения рабочего стола.
- Управление конфигурациями других оболочек.

## Приёмочные критерии

1. На поддерживаемых версиях macOS и Linux с предварительно установленным zsh установщик определяет ОС и пакетный менеджер, проверяет матрицу поддержки и автоматически устанавливает зависимости из системных или официальных upstream-источников без ручного редактирования абсолютных путей.
2. Если zsh отсутствует, установщик не устанавливает его и не заменяет конфигурацию; он завершает работу с инструкцией по предварительной установке zsh.
3. При наличии пользовательских файлов до установки они сохранены и их можно восстановить по инструкции.
4. Повторная установка не ломает существующее состояние и не дублирует изменения.
5. Новая оболочка загружает плагины из статического файла, созданного Antidote по списку, и показывает prompt Starship без сетевых запросов.
6. Если пакетный менеджер недоступен или не поддерживается, установщик прекращает работу до замены конфигурации и выводит точные инструкции для ручной установки.
7. Удаление установленной утилиты не делает запуск оболочки неработоспособным.
8. Удаление проекта удаляет только его помеченный блок в `.zshrc`, не затрагивая настройки Яндекс CLI и другие строки, добавленные пользователем или программами; резервные копии остаются доступными.
9. На системах, где пакеты предоставляют `fdfind` или `batcat`, сочетание `Ctrl+F` и соответствующие алиасы продолжают работать через привычные имена `fd` и `bat`.
10. При ошибке `zplugin-update` прежний статический файл загрузки сохраняется, а функция сообщает об ошибке и возвращает ненулевой код.
11. В проекте документированы поддерживаемые пакетные менеджеры, зависимости, команды установки, обновления, удаления и восстановления.

## Требования к версиям и поставке

- Для Starship требуется версия 1.22.0 или новее: конфигурация использует модуль `fill` и согласованные возможности prompt. Установщик обновляет более старую версию или использует официальный установщик Starship.
- Для остальных CLI-утилит проект не фиксирует минимальные версии: используются актуальные версии системных пакетов либо официальный способ установки upstream, если пакет недоступен.
- Имена пакетов и различия команд `fd`/`fdfind` и `bat`/`batcat` описаны в [матрице поддерживаемых платформ](поддерживаемые-платформы.md).
- Имена, расположение и формат файлов конфигурации задаются структурой репозитория: shell-файлы в `config/zsh/`, список плагинов в `.zsh_plugins.txt`, а конфигурации Starship — в TOML-файлах `config/`.
- Ручные сценарии установки, обновления и удаления описываются в `docs/`; корневой `README.md` является единственным документом вне `docs/`.
- Автоматические тесты в рамках первой реализации не запускаются; успешность установки проверяется вручную на поддерживаемых платформах перед выпуском.
